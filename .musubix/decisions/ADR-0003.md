# ADR-0003: Append-only hash-chained audit log for ELN tamper evidence

## Context / 背景
The ELN subsystem must meet 21 CFR Part 11/GxP-style requirements: an
immutable audit trail (REQ-ELN-005), tamper detection (REQ-ELN-011),
scheduled integrity checks (REQ-ELN-013), signature blocking on tamper
(REQ-ELN-014/020), and non-destructive void of signed records (REQ-ELN-015).

## Decision / 決定
Implement the audit trail as an append-only, hash-chained log: each entry
stores a canonical serialization of its payload, a strictly increasing
per-project sequence number, and the hash of the previous entry, so any
historical mutation breaks the chain. The chain is periodically anchored by
a checkpoint signed with a key that normal application database roles
cannot access, and the audit table itself is protected by database-level
privilege separation: the application's normal write role has INSERT-only
access, while UPDATE/DELETE grants exist only for a separate,
non-application-accessible maintenance role used solely for approved
disaster-recovery procedures. The scheduled integrity check recomputes and
verifies the chain (including the latest signed checkpoint) per project at
least every 24 hours. Electronic signatures are implemented as a distinct
subsystem (DES-AIRA2-007) that consults the audit/integrity subsystem's
`isSigningBlocked`/`clearedAwaitingScheduledCheck` state before accepting a
signature, keeping "detect tampering" and "gate signing" independently
testable, and only the audit subsystem's internal, trusted writer (not a
public API accepting arbitrary before/after payloads) may append entries,
invoked atomically from within DES-AIRA2-005/007's own state-changing
transactions.

## Rejected alternatives / 却下した代替案
- A general-purpose blockchain/distributed ledger — rejected as excessive
  operational complexity for a single-tenant-per-project audit log with no
  need for cross-organization consensus.
- Soft-delete flags with row-level "modified" timestamps only — rejected
  because it does not detect retroactive tampering with historical rows,
  only tracks the latest state.
- Combining signature gating logic directly inside the audit-log component
  — rejected because REQ-ELN-014 and REQ-ELN-020 have independently
  testable conditions (initial block vs. resumption-after-clean-recheck)
  that are clearer as a consuming subsystem's state machine.
- A hash chain alone with no database privilege separation or external
  checkpoint signing — rejected because a writer with UPDATE/DELETE
  privileges on the audit table (or direct database access) could rewrite
  a historical entry and recompute every subsequent hash, leaving a
  chain that still validates; the chain must be backed by an
  independently privileged, periodically anchored trust root to be
  tamper-evident against that realistic threat, not just against
  application-level API/UI paths.
- A public `appendAuditEntry` API taking arbitrary before/after payloads —
  rejected because it would let a caller record an audit entry that does
  not correspond to a committed state transition; the writer must be an
  internal call made atomically within the same transaction as the state
  change it describes.

## Consequences / 結果
Verifying integrity is an O(n) chain walk plus checkpoint-signature
verification per project per check; this is acceptable at expected ELN
record volumes but must be revisited if a project's audit trail grows very
large. Any future migration or backfill tooling must preserve the hash
chain and sequence numbering rather than bulk-inserting rows. Database
role/privilege configuration becomes a security-relevant deployment
artifact that must be reviewed alongside application code changes.
