# ADR-0006: Fastify HTTP runtime, SQLite persistence, and Vite/React SPA build

## Context / 背景
CHANGE-0001 delivered every AIRA2 backend service (DES-AIRA2-001..009) with
HTTP-shaped interfaces already documented in their `Interfaces:` fields
(e.g. `POST /auth/login/{method}`), and a frontend (DES-AIRA2-010) built as
in-process TypeScript controllers under a "minimal-contract" design with no
real HTTP server, no browser rendering, and no persistent storage — all
state lived only in process memory (`Map`-backed stores). CHANGE-0003
(REQ-RUNTIME-001..011) requires an actually startable server process, a
persistence layer surviving process restarts, and a browser-rendered SPA,
without discarding the already-approved service boundaries, authorization
model (ADR-0005), or existing component responsibilities.

## Decision / 決定
- **HTTP runtime: Fastify.** A single Node.js process (`npm run
  server:start`) hosts a Fastify HTTP server. Each existing component's
  already-documented REST-shaped interface becomes a real Fastify route
  registered in a new component, DES-AIRA2-012 (REST API Gateway & Chat
  Execution), which calls the existing in-process service methods
  unchanged. Fastify was chosen over Express for built-in JSON-schema
  request/response validation (useful for enforcing the REST-shaped
  contracts already specified in each component) and a smaller plugin
  surface than a full framework, at comparable startup speed.
- **Persistence: SQLite via `better-sqlite3`.** A new component,
  DES-AIRA2-011 (Runtime Server & Persistence), owns a single SQLite
  database file (default `./data/aira2.sqlite`, overridable by
  `AIRA2_DB_PATH` per REQ-RUNTIME-005) implementing the two row-ownership
  categories already defined by ADR-0005 (project-scoped rows with
  `project_id`; account-scoped/global rows with `owner_user_id` or none).
  Existing in-memory `Map`-backed stores in DES-AIRA2-001..009 are
  re-implemented against this store behind their already-existing method
  signatures, so no calling component's interface changes.
- **SPA build: Vite + React.** The DES-AIRA2-010 frontend is rendered by a
  Vite-built React SPA calling the Fastify REST API, replacing the
  minimal-contract controllers as the sole deployed UI (REQ-RUNTIME-004,
  REQ-RUNTIME-008). Vite was chosen for fast local dev startup and a
  standard `npm run build` production bundle Fastify can serve as static
  assets.
- **Chat as a first-class runtime capability**, not folded into an
  existing component: chat/agent execution (REQ-RUNTIME-011) has no
  pre-existing backend component (it was previously named only as a
  styling target in REQ-GUI-005), so it is implemented in DES-AIRA2-012
  directly on top of DES-AIRA2-004 (LLM Backend Gateway)'s existing
  `resolveBackend`/adapter interfaces, rather than creating a fourth new
  component for a single request/response endpoint.

## Rejected alternatives / 却下した代替案
- **Express instead of Fastify** — rejected; Express would work but lacks
  Fastify's built-in schema validation, which is used to keep the Fastify
  routes honest against each component's already-documented REST contract
  without a separate validation library.
- **PostgreSQL instead of SQLite** — rejected for this stage; the user
  explicitly requested a file-based, no-external-service database for
  local/single-node deployment (confirmed via clarifying question during
  requirements gathering). Revisiting this is future work if a
  multi-process/horizontally-scaled deployment is later required, since
  SQLite's single-writer model does not suit that.
- **Next.js/Remix full-stack framework instead of Fastify+Vite** —
  rejected; it would require re-hosting all nine existing backend
  components inside a framework-specific server runtime and restructuring
  their already-approved interfaces, which is unnecessary churn when a
  thin Fastify routing layer in front of unchanged existing components
  achieves the same requirements.
- **Merging DES-AIRA2-011 (persistence) and DES-AIRA2-012 (REST API) into
  one component** — rejected; persistence is a cross-cutting concern used
  by all nine existing components, while the REST API gateway is a thin
  routing layer with no storage of its own, so keeping them as separate
  components with a `Depends-On` edge (DES-AIRA2-012 → DES-AIRA2-011)
  matches their distinct responsibilities and matches this feature's
  existing convention of one component per responsibility.

## Consequences / 結果
Every existing component's already-documented HTTP interface becomes a real,
callable route without changing its method contract. Every one of
DES-AIRA2-001..009 gains a `Depends-On: DES-AIRA2-011` edge for storage,
and DES-AIRA2-011 itself has `Depends-On: none` — it is a foundation-layer
component with no dependency on any service that depends on it, avoiding a
storage/credential-bootstrap cycle. The one-time administrator
shared-credential bootstrap from environment variables is performed by
composition-root startup code using a trusted system principal (the same
pattern as DES-AIRA2-006's scheduler principal), not by DES-AIRA2-011
calling DES-AIRA2-003 as a runtime dependency. A single SQLite file is a
single point of write contention and a single-node deployment limit; this
is accepted for the current requirement scope (local/single-node runnable
server) and must be revisited before any multi-instance horizontal-scaling
requirement is introduced. SQLite's lack of a database-level user/role/GRANT
model means DES-AIRA2-006's audit privilege separation is approximated via
an application-level insert-only discipline plus OS file permissions,
documented explicitly in DES-AIRA2-011, rather than true DB-enforced role
separation; this is a known, accepted limitation of the SQLite choice for
this stage. Graph RAG's per-project `aira-graphdb` data remains its own
separately persisted store, not migrated into SQLite. The frontend build
(Vite/React) is a separate artifact from the server bundle and must be
served as static assets by the same Fastify process per REQ-RUNTIME-001.
