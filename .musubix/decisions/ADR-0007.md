# ADR-0007: Credential-version session invalidation and team-based effective-role resolution

## Context / 背景
CHANGE-0004 adds project invitations, teams, self-service profile/password/MFA
management, password reset, and session listing/revocation
(REQ-MULTIUSER-013..050). Two hard problems emerged during requirements
review (rubber-duck rounds 3, 5, and 6):

1. Password change/reset must invalidate existing sessions, but a naive
   "delete all session rows for this account" approach cannot close a race
   where a login already in flight — having verified the *old* password
   just before the reset committed — still issues a new session afterward
   using the old credential.
2. Project access can now come from three sources (direct owner assignment,
   direct share, or team membership), and a project's authorization decision
   must reflect all three consistently without duplicating role-resolution
   logic in every caller.

## Decision / 決定
- **Credential-version binding** (DES-AIRA2-015): every account carries a
  monotonically increasing credential version. Every issued session records
  the version read atomically with its own issuance (REQ-MULTIUSER-046).
  Every credential replacement (self-service change or reset) increments the
  version as part of the same atomic operation that replaces the credential
  (REQ-MULTIUSER-043/047). Session validation rejects any session whose
  recorded version no longer matches the account's current version
  (REQ-MULTIUSER-048). To close the in-flight-login race, login itself
  re-checks that the version observed at credential verification is still
  current immediately before issuing a session, failing the attempt instead
  of adopting the new version if it changed (REQ-MULTIUSER-050).
- **Team-based effective-role resolution** (DES-AIRA2-013): teams are a
  first-class entity independent of any project. A project's authorization
  matrix (DES-AIRA2-002) resolves the acting user's role through a pluggable
  role resolver — DES-AIRA2-013's `resolveEffectiveRole`, returning the
  most-permissive of owner assignment, direct share, and any team-based share
  for a team the user currently belongs to (REQ-MULTIUSER-031) — registered
  at composition-root startup rather than DES-AIRA2-002 depending directly on
  DES-AIRA2-013, avoiding a dependency cycle (DES-AIRA2-013 already depends
  on DES-AIRA2-002 for `authorize()`).

## Rejected alternatives / 却下した代替案
- A session revocation list/blacklist checked on every request — rejected
  because it requires an unbounded, ever-growing list (or a cleanup job) and
  does not by itself solve the in-flight-login race: a login that verifies
  the old password concurrently with a reset could still complete and add a
  *new*, not-yet-blacklisted session after the blacklist snapshot is taken.
  The credential-version approach instead makes staleness self-evident from
  the account's current state, and the explicit re-check at issuance closes
  the race at its source.
- Deleting all session rows synchronously inside the reset transaction only
  — rejected because it does not prevent a session created by a
  concurrently in-flight login from being added immediately afterward with
  the old credential; the version re-check at issuance is required in
  addition to any invalidation of pre-existing sessions.
- Modeling teams as an ad hoc "group of direct shares" created transparently
  whenever a team grant is made (i.e., materializing one direct share row
  per team member instead of a distinct team-share row) — rejected because
  it silently duplicates state that drifts out of sync when team membership
  changes later (REQ-MULTIUSER-017 requires subsequently added members to
  gain access automatically) and makes REQ-MULTIUSER-026's team-removal
  session/MCP termination unable to distinguish "access derived solely from
  this team" from a separate direct share, breaking the requirement's
  precision.
- Having DES-AIRA2-002 depend directly on DES-AIRA2-013 for role resolution
  — rejected because DES-AIRA2-013 already depends on DES-AIRA2-002 for its
  own `authorize()` calls (invitation/member-management actions), and a
  direct two-way dependency would be a cycle; the pluggable resolver
  registered at composition-root avoids it, matching the existing
  service-account-modify precedent between DES-AIRA2-001/002.

## Consequences / 結果
Every new code path that issues a session (login, password change,
password reset) must go through DES-AIRA2-015's `issueSession`, never
construct a session record directly, or the version-binding guarantee is
silently bypassed. Every code path that replaces a credential must call
`incrementCredentialVersion` inside the same atomic operation, or
REQ-MULTIUSER-047/048's invariant is broken. Team-share rows remain
distinct from direct-share rows indefinitely; DES-AIRA2-013's removal-time
termination logic (REQ-MULTIUSER-026) depends on this distinction and must
not be "simplified" into a single shares table without a `source` column
that preserves it. DES-AIRA2-002's authorize() must resolve roles only
through the registered resolver, never re-implement owner/share/team
lookup logic locally, so a single trace of truth is maintained.
