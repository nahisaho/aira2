# ADR-0005: Shared multi-tenant database with enforced project-scoped row access

## Context / 背景
AIRA2 must isolate users' projects, files, conversations, and settings by
default, support explicit sharing with role-based access, revoke access
while preserving historical signed-record attribution, and enforce a
documented authorization matrix across ELN and Graph RAG actions
(REQ-MULTIUSER-003..012). The GUI must reflect only permitted actions.

## Decision / 決定
Use a single shared database, distinguishing two row-ownership categories:

- **Project-scoped rows** (ELN records/protocols/audit entries, Graph RAG
  indexes, project-level LLM backend overrides, project-scoped credential
  grants, Agent Skills/MCP project configuration) carry a mandatory
  `project_id` column and are protected by `authorize(actorContext,
  projectId, action)` against DES-AIRA2-002's project-scoped matrix.
- **Account-scoped or global rows** (a user's own default LLM backend
  preference, a user's personal credential override, admin-shared
  credentials) carry `owner_user_id` (or no project reference at all for
  global admin data) instead of `project_id`, and are protected by
  `authorizeSelf(actorContext, action)` against DES-AIRA2-002's self-scope
  matrix, or by a direct global-admin-role check for admin-only data —
  never by the project-scoped matrix, since no project is involved.

Enforce both categories centrally in the Project Authorization & Sharing
Service (DES-AIRA2-002), which every other backend component with
tenant- or account-scoped data (DES-AIRA2-003 Credential Vault,
DES-AIRA2-004 LLM Backend Gateway, DES-AIRA2-005 ELN Core, DES-AIRA2-006
ELN Audit & Integrity, DES-AIRA2-007 ELN Approval & Signature,
DES-AIRA2-008 Agent Skills/MCP Configuration, DES-AIRA2-009 Graph RAG) and
the frontend (DES-AIRA2-010) must call through `authorize()` (project-scoped
actions) or `authorizeSelf()` (account-scoped actions) before reading or
writing the corresponding rows, using a trusted actorContext established
by DES-AIRA2-001 rather than a bare caller-supplied user/project ID; no
component may query project- or account-scoped tables directly using only
a caller-supplied ID without one of these checks. The frontend additionally
uses the same authorization matrices to decide which actions to render, as
a UX convenience only, not as a security boundary.

## Rejected alternatives / 却下した代替案
- Separate database schema per tenant — rejected due to high operational
  overhead (migrations, backups, connection pooling) at expected AIRA2
  scale, and no requirement demands physical data separation.
- Separate database instance per user — rejected as cost- and
  operations-prohibitive for an individual/team collaboration tool.
- Enforcing authorization only in the frontend — rejected outright as a
  security failure; the frontend constraint above is explicit that
  server-side enforcement in DES-AIRA2-002 is mandatory and the frontend
  check is cosmetic only.
- Letting individual components (Vault, LLM Gateway, ELN, Graph RAG)
  perform their own ad hoc ownership checks — rejected because it was
  found, on review, to produce inconsistent enforcement and paths that
  bypassed the matrix entirely; every tenant-scoped component must depend
  on and call the one shared DES-AIRA2-002 service instead.
- Forcing every row, including purely personal user preferences and
  admin-global credentials, into the project-scoped `authorize(...,
  projectId, ...)` model — rejected because some data (a user's own
  default backend choice, a user's personal credential override,
  admin-shared credentials) has no project to scope against; requiring a
  projectId there produced an unimplementable contract on review, so
  DES-AIRA2-002 instead exposes a second, explicitly self-scope
  `authorizeSelf()` check for exactly that data.

## Consequences / 結果
All new project-scoped tables and API endpoints must be reviewed for a
mandatory `authorize()` call, and all new account-scoped/global ones for a
mandatory `authorizeSelf()` call (or direct global-admin-role check); missing
either is a security regression, not just a bug. Query performance depends
on `project_id`/`owner_user_id` indexing discipline. Revocation and
audit-log requirements (REQ-MULTIUSER-005/006/008/012) are implementable as
operations against this single authorization service without
cross-database coordination. Every project-scoped component now carries an
explicit `Depends-On: DES-AIRA2-002` edge, which is intentional and must
not be removed as a "simplification." Every action referenced in a
component's Constraints field must have a corresponding row in one of
DES-AIRA2-002's two matrices; adding a new authorize()/authorizeSelf() call
without also adding its action to the matrix is treated as a design defect.
