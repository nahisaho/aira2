# Design / 設計

## DES-AIRA2-001: Authentication Service / 認証サービス
Responsibilities: Authenticate users via GitHub OAuth, email/password, and SSO/OIDC; issue and validate sessions; enforce that each account is uniquely bound to one natural person and flag shared/service accounts as non-signing.
Interfaces: POST /auth/login/{method}, POST /auth/logout, GET /auth/session, POST /auth/accounts/{id}/mark-service-account (actorContext, action `account.service-account.modify`, enforced as a direct global-admin-role check against `actorContext.roles` — issued by this same service during authentication — rather than a call to DES-AIRA2-002, since DES-AIRA2-001 must not depend on DES-AIRA2-002), AuthProvider SPI implemented per method (github-oauth, password, oidc).
Constraints: Must not allow two natural persons to share one account credential; must present all enabled methods on the login screen without preferring one by default; session tokens must be revocable server-side within a bounded time; marking/unmarking an account as a shared service account requires the caller's `actorContext.roles` to include global-admin (action `account.service-account.modify`, listed in DES-AIRA2-002's self-scope matrix for documentation/matrix-completeness only — DES-AIRA2-001 enforces it locally to avoid a Depends-On cycle with DES-AIRA2-002), never the target account's own consent.
Requirements: REQ-MULTIUSER-001 REQ-MULTIUSER-002 REQ-MULTIUSER-007 REQ-MULTIUSER-010
ADRs: ADR-0002
Depends-On: DES-AIRA2-011

## DES-AIRA2-002: Project Authorization & Sharing Service / プロジェクト認可・共有サービス
Responsibilities: Enforce default per-user project isolation; manage explicit project sharing and role grants (owner, editor, viewer); revoke access and terminate active sessions/MCP connections on revocation while preserving prior signed-record attribution; own and define the concrete project-scoped and self-scope authorization matrices below (covering ELN, Graph RAG, LLM backend configuration, and Agent Skills/MCP configuration actions), and be the enforcement point for every row via `authorize()`/`authorizeSelf()` EXCEPT `account.service-account.modify`, whose policy it defines but whose enforcement is delegated to DES-AIRA2-001 (see that row's note) because authentication must not depend on this service; record a per-user audit log of authorization-relevant actions.
Interfaces: POST /projects/{id}/shares (actorContext, ``authorize(actorContext, projectId, 'project.share.manage')``), DELETE /projects/{id}/shares/{userId} (actorContext, ``authorize(actorContext, projectId, 'project.share.manage')``), GET /projects/{id}/authz-matrix, authorize(actorContext, projectId, action) -> allow|deny, authorizeSelf(actorContext, action) -> allow|deny (for actions scoped only to the caller's own account, no projectId required), on-revoke webhook to Session Service and MCP Gateway.
Constraints: Deny-by-default for any action not explicitly present in the authorization matrix. Concrete project-scoped matrix (rows = action, columns = owner/editor/viewer; Y=allowed, N=denied): project.share.manage Y/N/N; eln.view Y/Y/Y; eln.create Y/Y/N; eln.edit Y/Y/N; eln.approve Y/N/N; eln.sign Y/Y/N; eln.void Y/N/N; eln.export Y/Y/N; eln.audit-history.view Y/Y/N; eln.audit-integrity.manage Y/N/N; eln.audit-integrity.view Y/Y/N; graphrag.view Y/Y/Y; graphrag.create Y/Y/N; graphrag.modify Y/N/N; llmbackend.project-override.view Y/Y/Y; llmbackend.project-override.modify Y/N/N; credential.project.use Y/Y/N; credential.project.view Y/N/N; agent-skills.view Y/Y/Y; agent-skills.modify Y/Y/N; mcp-config.view Y/Y/Y; mcp-config.modify Y/Y/N; agent-skill-source.manage Y/Y/N; agent-skill-source.sync Y/Y/N; mcp-provider.enable Y/Y/N; llmbackend.chat.execute Y/Y/Y. Self-scope matrix (rows = action, single column = policy; checked by `authorizeSelf(actorContext, action)` with no project role involved, EXCEPT the one explicitly-noted exception below): llmbackend.user-default.modify (any authenticated user, own account only); credential.user-override.modify (any authenticated user, own account only); credential.self.view (any authenticated user, own account only); llmbackend.admin-credential.modify (caller's global admin role only, checked directly against the account's role from DES-AIRA2-001 — this is the sole authoritative rule for that action; no project-scoped row for it exists or is needed); account.service-account.modify (caller's global admin role only — POLICY OWNED HERE, but ENFORCEMENT IS DELEGATED to DES-AIRA2-001, which performs a local direct `actorContext.roles` check rather than calling `authorizeSelf` on this service, because DES-AIRA2-001 must not depend on DES-AIRA2-002; this row exists for matrix-completeness and policy documentation only, and is the one deliberate exception to this service being the sole enforcement point). Revocation must not alter historical signature attribution (REQ-MULTIUSER-012). Every action cited in any component's Interfaces or Constraints must have exactly one matching row in one of these two matrices; adding a new `authorize()`/`authorizeSelf()` call without a corresponding matrix row is a design defect. Every other backend component must call `authorize()` (for project-scoped actions) or `authorizeSelf()` (for self-scoped actions) through this service using a trusted actorContext (established by DES-AIRA2-001) rather than a bare caller-supplied userId/projectId; no component may query tenant-scoped rows without a preceding `authorize()`/`authorizeSelf()` call.
Requirements: REQ-MULTIUSER-003 REQ-MULTIUSER-004 REQ-MULTIUSER-005 REQ-MULTIUSER-006 REQ-MULTIUSER-008 REQ-MULTIUSER-009 REQ-MULTIUSER-011 REQ-MULTIUSER-012
ADRs: ADR-0005
Depends-On: DES-AIRA2-001 DES-AIRA2-011

## DES-AIRA2-003: Credential Vault / 認証情報保管庫
Responsibilities: Store LLM provider API keys and OAuth tokens encrypted at rest; hold administrator shared credentials and per-user override credentials; mask secret values on any read path; reject any credential write/read request the caller's authorized trust context does not permit for that scope.
Interfaces: setAdminSharedCredential(actorContext, provider, secret) -> credentialRef (``authorizeSelf(actorContext, 'llmbackend.admin-credential.modify')``, global admin role only), setUserOverrideCredential(actorContext, provider, secret) -> credentialRef (``authorizeSelf(actorContext, 'credential.user-override.modify')``, self-scope only, no projectId required), getCredentialForRequest(actorContext, projectId, provider) -> resolved secret (server-side only, `authorize(actorContext, projectId, 'credential.project.use')` via DES-AIRA2-002, actorContext carries the caller's authorized identity/roles), listProjectCredentials(actorContext, projectId) -> masked entries (`authorize(actorContext, projectId, 'credential.project.view')` via DES-AIRA2-002), listSelfCredentials(actorContext) -> masked entries (``authorizeSelf(actorContext, 'credential.self.view')``, no projectId required).
Constraints: Plaintext secrets must never leave the vault process boundary; masked entries show only a fixed-length suffix; encryption keys must be rotatable without invalidating stored credential rows; every project-scoped method call (`getCredentialForRequest` via `credential.project.use`, `listProjectCredentials` via `credential.project.view`) must resolve `authorize(actorContext, projectId, action)` via DES-AIRA2-002 before touching stored secrets; every self-scoped or admin-global method call (`setUserOverrideCredential`, `listSelfCredentials`, `setAdminSharedCredential`) must instead resolve `authorizeSelf(actorContext, action)`, since none of these carries a projectId; all use a trusted actorContext propagated from DES-AIRA2-001/DES-AIRA2-002 rather than a bare caller-supplied userId/projectId.
Requirements: REQ-LLMBACKEND-003 REQ-LLMBACKEND-004 REQ-LLMBACKEND-005 REQ-LLMBACKEND-007
ADRs: ADR-0002
Depends-On: DES-AIRA2-001 DES-AIRA2-002 DES-AIRA2-011

## DES-AIRA2-004: LLM Backend Gateway / LLMバックエンドゲートウェイ
Responsibilities: Provide one adapter-based abstraction over GitHub Copilot CLI, OpenAI, Azure OpenAI, and Anthropic; let a user set their own default provider and let a project owner set a project-level override; resolve the effective backend for a request using project-override-then-user-default precedence; surface a user-visible fallback notice on backend failure; expose configured embedding-capability information per backend to Graph RAG.
Interfaces: LlmBackendAdapter { chat(), embed(), streamAgent() } implemented per provider, setUserDefaultBackend(actorContext, provider) (``authorizeSelf(actorContext, 'llmbackend.user-default.modify')``, no projectId required), setProjectBackendOverride(actorContext, projectId, provider) (``authorize(actorContext, projectId, 'llmbackend.project-override.modify')`` via DES-AIRA2-002, owner only per the matrix's Y/N/N row — no separate project-admin role exists), resolveBackend(actorContext, projectId) -> providerConfig (``authorize(actorContext, projectId, 'llmbackend.project-override.view')`` via DES-AIRA2-002), onBackendFailure(providerId) -> notice event, getEmbeddingCapabilities(providerId) -> matrix entry.
Constraints: Adapters must expose a common request/response contract regardless of provider; adding a fifth provider must not require changes to callers of resolveBackend; failure fallback must not silently switch providers without a visible notice; every call that reads or writes project-scoped backend configuration — including `resolveBackend` (action `llmbackend.project-override.view`) and `setProjectBackendOverride` (action `llmbackend.project-override.modify`), and not only configuration-changing calls — must pass an `authorize(actorContext, projectId, action)` check via DES-AIRA2-002 before DES-AIRA2-003 is touched; every call scoped only to the caller's own account (`setUserDefaultBackend`, action `llmbackend.user-default.modify`) must instead pass an `authorizeSelf(actorContext, action)` check, since it has no projectId.
Requirements: REQ-LLMBACKEND-001 REQ-LLMBACKEND-002 REQ-LLMBACKEND-006 REQ-LLMBACKEND-008
ADRs: ADR-0002
Depends-On: DES-AIRA2-002 DES-AIRA2-003 DES-AIRA2-011

## DES-AIRA2-005: ELN Core Service / ELNコアサービス
Responsibilities: Manage structured experiment records and their immutable, content-hashed versions; manage protocol/SOP authoring, versioning, and immutable version linkage from experiment records, enforcing that a linked protocol version's approval status (set only by DES-AIRA2-007) is "approved" before the link is accepted; link samples/reagents/inventory context into records; provide ELN search and reporting; integrate computational provenance references from executed notebooks.
Interfaces: POST /projects/{projectId}/eln/records (actorContext, `eln.create`; creates recordVersionId v1), PATCH /projects/{projectId}/eln/records/{id} (actorContext, `eln.edit`; creates a new immutable recordVersionId, content hash, and predecessor link; never mutates a prior version), GET /projects/{projectId}/eln/records/{id} (actorContext, `eln.view`), POST /projects/{projectId}/eln/records/{id}/export (actorContext, `eln.export`), DELETE /projects/{projectId}/eln/records/{id} (actorContext, `eln.void`; unsigned records only, see DES-AIRA2-007 for signed-record void), POST /projects/{projectId}/eln/protocols (actorContext, `eln.create`), POST /projects/{projectId}/eln/protocols/{id}/versions (actorContext, `eln.edit`), GET /projects/{projectId}/eln/search (actorContext, `eln.view`), GET /projects/{projectId}/eln/records/{id}/provenance (actorContext, `eln.view`), internal markProtocolVersionStatus(protocolVersionId, status) callable only by DES-AIRA2-007.
Constraints: Editing an experiment record must always create a new immutable, content-hashed version, never overwrite a prior one; a record's linked protocol version reference is immutable once set and must reference a protocol version whose status is "approved"; every state-changing command (create, edit, void, delete) must execute inside one atomic transaction that also commits the corresponding audit event via DES-AIRA2-006's internal writer — a command that cannot also commit its audit event must fail entirely; inventory/provenance links are read-only references to their source systems; all record/protocol reads and writes must resolve `authorize()` via DES-AIRA2-002 using a trusted actorContext.
Requirements: REQ-ELN-001 REQ-ELN-002 REQ-ELN-003 REQ-ELN-019 REQ-ELN-007 REQ-ELN-012 REQ-ELN-008 REQ-ELN-009
ADRs: ADR-0003
Depends-On: DES-AIRA2-002 DES-AIRA2-006 DES-AIRA2-011

## DES-AIRA2-006: ELN Audit & Integrity Subsystem / ELN監査・整合性サブシステム
Responsibilities: Provide an internal, trusted-only audit writer that DES-AIRA2-005 and DES-AIRA2-007 call within their own state-changing transactions (never exposed as a public API taking arbitrary before/after payloads) to append an immutable, chronologically ordered, per-project monotonically sequenced audit entry for every create/edit/view-sensitive/approve/void/export/delete action; run scheduled audit-trail integrity checks at least every 24 hours against a canonical, hash-chained representation of the log; block new electronic signature operations on tamper detection; track a `clearedAwaitingScheduledCheck` state after alert clearance and only lift the signing block when the next scheduled (not ad hoc) integrity check for that project completes clean.
Interfaces: appendAuditEntry(txContext, action, projectId, subjectType, subjectVersionId, actorContext) [internal, callable only from within a DES-AIRA2-005/007 transaction; `subjectType` is `record` or `protocol` and `subjectVersionId` is the corresponding immutable `recordVersionId`/`protocolVersionId` so both record-level and protocol-approval events are unambiguously attributable], runIntegrityCheck(schedulerContext, projectId) [internal, `trigger=scheduled`, callable only by the trusted scheduler service principal], runManualIntegrityCheck(actorContext, projectId) -> report [`trigger=manual`, `authorize(actorContext, projectId, 'eln.audit-integrity.manage')`], clearTamperAlert(actorContext, projectId) [`authorize(actorContext, projectId, 'eln.audit-integrity.manage')`, transitions to clearedAwaitingScheduledCheck], isSigningBlocked(actorContext, projectId) -> boolean [`authorize(actorContext, projectId, 'eln.audit-integrity.view')`], getChainCheckpoint(actorContext, projectId) -> externally-anchored signed checkpoint [`authorize(actorContext, projectId, 'eln.audit-integrity.view')`].
Constraints: Audit entries are stored in an append-only store with database-level privilege separation (the application's normal write role has no UPDATE/DELETE grant on the audit table; only a separate, non-application-accessible maintenance role does); each entry's hash covers a canonical serialization of the payload plus a strictly increasing per-project sequence number and the previous entry's hash; the hash chain is periodically anchored by a checkpoint signed with a key unavailable to normal application writers, and that checkpoint/report is itself protected by the same tamper-evidence guarantee; only a scheduled integrity check that runs after `clearTamperAlert` may clear `clearedAwaitingScheduledCheck` and unblock signing — a manual check never can, regardless of caller role; every externally reachable read or write (manual check, alert clearance, signing-blocked query, checkpoint read) must resolve `authorize()` via DES-AIRA2-002 using a trusted actorContext and the concrete `eln.audit-integrity.manage`/`eln.audit-integrity.view` actions in DES-AIRA2-002's matrix; only the internal scheduled trigger is exempt, and it authenticates via a trusted scheduler service principal rather than a user-supplied actorContext.
Requirements: REQ-ELN-005 REQ-ELN-011 REQ-ELN-013 REQ-ELN-014 REQ-ELN-020
ADRs: ADR-0003
Depends-On: DES-AIRA2-002 DES-AIRA2-011

## DES-AIRA2-007: ELN Protocol Approval & Electronic Signature Subsystem / プロトコル承認・電子署名サブシステム
Responsibilities: Run the protocol approval workflow, and be the sole component permitted to set a protocol version's status to "approved" via DES-AIRA2-005's internal status callback; apply electronic signatures gated by unique-person re-authentication, binding each signature to one immutable recordVersionId/protocolVersionId and its content hash so a later edit cannot retroactively change what was signed; enforce separation of duties between author and approver; forbid automated/impersonated signatures; restrict edits to signed/approved records to non-destructive void (new successor versions may still be created and separately signed).
Interfaces: POST /projects/{projectId}/eln/protocols/{id}/versions/{versionId}/approve (actorContext, `eln.approve`), POST /projects/{projectId}/eln/records/{id}/versions/{versionId}/sign (actorContext, `eln.sign`; requires fresh re-auth challenge and the caller-supplied content hash to match the stored version's hash, using optimistic-concurrency preconditions), POST /projects/{projectId}/eln/records/{id}/void (actorContext, `eln.void`), GET /projects/{projectId}/eln/records/{id}/signature-status (actorContext, `eln.view`).
Constraints: A signature request must re-verify the signer's live credential (REQ-ELN-016), must reject if the signer account is not uniquely bound to one person (REQ-MULTIUSER-010) or is the same person as the record author where separation of duties applies, and must reject if the target recordVersionId's content hash has changed since the client last read it; every state-changing command (approve, sign, void) must execute inside one atomic transaction that also commits the corresponding audit event via DES-AIRA2-006's internal writer; only when DES-AIRA2-006 reports the project as not signing-blocked may a signature be accepted; all approval/signature reads and writes must resolve `authorize()` via DES-AIRA2-002 using a trusted actorContext.
Requirements: REQ-ELN-004 REQ-ELN-006 REQ-ELN-016 REQ-ELN-017 REQ-ELN-018 REQ-ELN-010 REQ-ELN-015
ADRs: ADR-0003
Depends-On: DES-AIRA2-002 DES-AIRA2-005 DES-AIRA2-006 DES-AIRA2-001 DES-AIRA2-011

## DES-AIRA2-008: Agent Skills & MCP Configuration Manager / Agent Skills・MCP設定マネージャー
Responsibilities: Manage per-project Agent Skills definitions and per-project MCP server configuration using the same file/config layout as AIRA; register one or more external Agent Skills repositories per project and synchronize skills from them on demand; act as the registration point through which built-in MCP providers (e.g. DES-AIRA2-009) are enabled per project using the same configuration surface as user-added MCP servers.
Interfaces: GET /projects/{projectId}/agent-skills (actorContext, `agent-skills.view`), PUT /projects/{projectId}/agent-skills (actorContext, `agent-skills.modify`), GET /projects/{projectId}/mcp-servers (actorContext, `mcp-config.view`), PUT /projects/{projectId}/mcp-servers (actorContext, `mcp-config.modify`), POST /projects/{projectId}/agent-skill-sources (actorContext, `agent-skill-source.manage`; register an external repository with its access credential), GET /projects/{projectId}/agent-skill-sources/{sourceId} (actorContext, `agent-skills.view`), DELETE /projects/{projectId}/agent-skill-sources/{sourceId} (actorContext, `agent-skill-source.manage`), POST /projects/{projectId}/agent-skill-sources/{sourceId}/sync (actorContext, `agent-skill-source.sync`; shows a diff before applying), POST /projects/{projectId}/mcp-servers/builtin/{providerId}/enable (actorContext, `mcp-provider.enable`).
Constraints: Configuration format and directory layout must remain compatible with AIRA so existing project configurations can be imported without transformation; sync must not silently overwrite local project-specific edits without a diff/confirmation step; every interface (view or modify agent skills, view or modify MCP server config, register/list/remove a repository source, sync a source, enable a built-in provider) must resolve `authorize(actorContext, projectId, action)` via DES-AIRA2-002 first, using distinct actions (`agent-skills.view`, `agent-skills.modify`, `mcp-config.view`, `mcp-config.modify`, `agent-skill-source.manage`, `agent-skill-source.sync`, `mcp-provider.enable`); registering, removing, or syncing a source and enabling a built-in provider require project owner/editor authorization, while viewing requires only project-member access.
Requirements: REQ-AGENTCONFIG-001 REQ-AGENTCONFIG-002 REQ-AGENTCONFIG-003
ADRs: ADR-0004
Depends-On: DES-AIRA2-002 DES-AIRA2-011

## DES-AIRA2-009: Graph RAG Service (aira-synapse merge) / Graph RAGサービス(aira-synapse統合)
Responsibilities: Provide, per project that has enabled it through DES-AIRA2-008, a built-in MCP server backed by its own supervised, project-isolated aira-graphdb (Rust) process and data directory; index documents and answer hybrid queries with resolvable citations; keep generation-time LLM backend consistent with the requesting project's configured backend; maintain a documented embedding-capability matrix (per LLM provider: native-embedding-capable yes/no, and the fallback embedding provider/model to use when not) and require re-indexing when a project's effective embedding model changes; support federated queries across only the projects the requesting user can access.
Interfaces: MCP tools index_documents(actorContext, projectId, docs) (``authorize(actorContext, projectId, 'graphrag.create')``), query(actorContext, projectId|projectIds, question) -> answer + citations[{sourceDocumentId, sourceDocumentVersion, locator}] (``authorize(actorContext, projectId, 'graphrag.view')`` per accessible project, for federated calls), stats(actorContext, projectId) -> node/entity/edge counts (``authorize(actorContext, projectId, 'graphrag.view')``), getEmbeddingCapabilities() -> {providerId: {nativeEmbedding: bool, fallbackProvider, fallbackModel}}, POST /projects/{projectId}/graphrag/reindex (actorContext required, `authorize(actorContext, projectId, 'graphrag.modify')`).
Constraints: Each enabled project gets its own supervised aira-graphdb process instance and isolated data directory/database, keyed by projectId; a crashed process must be restarted automatically without losing that project's indexed state and without any cross-project data access; a federated query must silently drop projects the requesting user cannot access (verified via DES-AIRA2-002's `graphrag.view` check per project) rather than erroring; every answer must include at least one citation resolvable to an indexed source document version, or the answer must not be returned; changing the active embedding model for a project marks its existing indexed vectors stale and excludes them from query results until re-indexed; `index_documents` requires `graphrag.create`, `query`/`stats` require `graphrag.view`, and the reindex endpoint requires `graphrag.modify`, each resolved via DES-AIRA2-002 using a trusted actorContext.
Requirements: REQ-GRAPHRAG-001 REQ-GRAPHRAG-002 REQ-GRAPHRAG-003 REQ-GRAPHRAG-004 REQ-GRAPHRAG-005 REQ-GRAPHRAG-006 REQ-GRAPHRAG-013 REQ-GRAPHRAG-014 REQ-GRAPHRAG-015

## DES-AIRA2-011: Runtime Server & Persistence / 実行サーバーと永続化
Responsibilities: Host the single startable Node.js HTTP server process (`npm run server:start`) that serves both the REST API (via DES-AIRA2-012) and the built SPA (DES-AIRA2-010) on one configurable port; expose the `/healthz` endpoint; own the single SQLite-backed store implementing ADR-0005's project-scoped and account-scoped/global row categories, giving every existing component (DES-AIRA2-001..009) a durable table/adapter behind its unchanged method signatures in place of its previous in-memory `Map`, with per-component transaction boundaries preserved exactly as already specified (e.g. DES-AIRA2-005's create/edit/void commands and DES-AIRA2-006's audit append remain one atomic transaction); read `PORT`/`AIRA2_DB_PATH`/`AIRA2_SHARED_CREDENTIAL_<PROVIDER>` environment variables at startup, and, before the HTTP listener accepts any request, run a composition-root startup step (not a call from within DES-AIRA2-011's own runtime logic) that uses a trusted system principal — the same pattern as DES-AIRA2-006's `schedulerContext` — to invoke DES-AIRA2-003's `setAdminSharedCredential` for each present `AIRA2_SHARED_CREDENTIAL_<PROVIDER>` only when no credential is already stored for that provider. Graph RAG's per-project `aira-graphdb` process and data directory (DES-AIRA2-009) remains its own separately persisted, file-backed store outside this shared SQLite database; DES-AIRA2-011 is responsible only for ensuring that data directory's path is itself a persistent (non-temporary) location that survives a process restart, not for migrating Graph RAG's internal vector/graph format into SQLite. Because SQLite has no database-level user/role/GRANT model, DES-AIRA2-006's audit-table privilege separation is realized, for this persistence engine, as: the audit table lives in its own SQLite connection/file that the running server process only ever issues `INSERT` statements against (no code path in DES-AIRA2-001..009/011/012 ever issues `UPDATE`/`DELETE` against it), protected by an OS-level file-permission boundary restricting write access to the server process's own account, with any correction only possible through a separate offline maintenance tool run by an operator outside the running server process — approximating, not replacing, true DB-role separation.
Interfaces: startServer(config) -> ListeningServer, GET /healthz -> {status:"ok"}, SqliteStore { get/put/query per row category, keyed by project_id or owner_user_id per ADR-0005, plus a separate append-only connection/file for DES-AIRA2-006's audit table }, loadEnvConfig() -> {port, dbPath, sharedCredentials}.
Constraints: Must not expose `/healthz` or any static asset route as an authorization bypass for other routes; the SQLite store must preserve every existing component's data-shape/query contract and transaction-atomicity guarantees exactly (no behavior change to DES-AIRA2-001..009's already-approved semantics); the startup credential-bootstrap step must never overwrite a credential already present in the store, regardless of whether the environment value changed (REQ-RUNTIME-010), and must run only as trusted composition-root startup code, never as an HTTP-reachable path; startup must not block on the health endpoint being reachable for more than 5 seconds.
Requirements: REQ-RUNTIME-001 REQ-RUNTIME-002 REQ-RUNTIME-005 REQ-RUNTIME-006 REQ-RUNTIME-009 REQ-RUNTIME-010
ADRs: ADR-0005 ADR-0006
Depends-On: none

## DES-AIRA2-012: REST API Gateway & Chat Execution / REST APIゲートウェイ・チャット実行
Responsibilities: Register a Fastify route for every REST-shaped interface already documented in DES-AIRA2-001..002/003..009 (auth/session, LLM backend/credential settings, ELN records/signatures/audit history, Graph RAG, project membership/sharing/roles, Agent Skills/MCP configuration), calling each existing component's method unchanged rather than reimplementing its logic; for every route other than session-establishment (login, registration, OAuth/OIDC callback), validate the caller's session via DES-AIRA2-001 and construct the trusted `actorContext` server-side from it — an HTTP caller never supplies `actorContext` directly — before invoking the underlying component, which then applies its own already-approved `authorize()`/`authorizeSelf()` check; provide a new chat/agent-execution endpoint on top of DES-AIRA2-004's `resolveBackend`/adapter interfaces, authorized via a new `llmbackend.chat.execute` action added to DES-AIRA2-002's project-scoped matrix (Y/Y/Y for owner/editor/viewer, matching the existing read-oriented `graphrag.view`/`eln.view` rows, since chat is a per-request pass-through rather than configuration).
Interfaces: Fastify route table mapping each documented `POST/GET/PATCH/DELETE` interface in DES-AIRA2-001..002/003..009 to that component's existing method, each preceded by a session-validation pre-handler that builds the trusted actorContext (except session-establishment routes); POST /projects/{projectId}/chat (message) -> backend response (`authorize(actorContext, projectId, 'llmbackend.chat.execute')` via DES-AIRA2-002, then resolves the effective backend via DES-AIRA2-004's `resolveBackend`).
Constraints: Must not duplicate business logic already present in DES-AIRA2-001..002/003..009 — a route handler only translates HTTP request/response to/from an existing method call; must never accept an HTTP-supplied `actorContext` field, constructing it only from a validated session; every route other than login/registration/OAuth-OIDC-callback must reject an unauthenticated caller before invoking the underlying component (REQ-RUNTIME-007); the chat route must resolve `llmbackend.chat.execute` via DES-AIRA2-002 before calling DES-AIRA2-004, and must identify the failing provider on backend failure per REQ-LLMBACKEND-006 rather than silently switching providers.
