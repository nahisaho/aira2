# Design / 設計

## DES-AIRA2-001: Authentication Service / 認証サービス
Responsibilities: Authenticate users via GitHub OAuth, email/password, and SSO/OIDC; issue and validate sessions; enforce that each account is uniquely bound to one natural person and flag shared/service accounts as non-signing; for an account with an active TOTP second factor, or while a deployment-level setting requires MFA for any account, obtain a valid-TOTP determination through a pluggable `MfaCheck` extension (implemented by DES-AIRA2-014, registered at composition-root startup — DES-AIRA2-001 does not depend on DES-AIRA2-014 to avoid a dependency cycle, since DES-AIRA2-014 itself depends on DES-AIRA2-001 for actorContext trust) before attempting to issue a session; delegate the actual session issuance to a pluggable `SessionIssuer` extension (implemented by DES-AIRA2-015, registered the same way, for the same cycle-avoidance reason) via a single atomic conditional call that re-checks both credential-version currency and MFA eligibility at the moment of issuance, so that neither can go stale between credential verification and session creation.
Interfaces: POST /auth/login/{method}, POST /auth/logout, GET /auth/session, POST /auth/accounts/{id}/mark-service-account (actorContext, action `account.service-account.modify`, enforced as a direct global-admin-role check against `actorContext.roles` — issued by this same service during authentication — rather than a call to DES-AIRA2-002, since DES-AIRA2-001 must not depend on DES-AIRA2-002), AuthProvider SPI implemented per method (github-oauth, password, oidc); login flow calls the registered `MfaCheck.verify(accountId, code)` when a second factor is active or deployment-required, then calls the registered `SessionIssuer.issueSessionIfEligible(accountId, versionAtVerification, mfaSatisfied)` exactly once as the final step before returning a session or a failure.
Constraints: Must not allow two natural persons to share one account credential; must present all enabled methods on the login screen without preferring one by default; session tokens must be revocable server-side within a bounded time; marking/unmarking an account as a shared service account requires the caller's `actorContext.roles` to include global-admin (action `account.service-account.modify`, listed in DES-AIRA2-002's self-scope matrix for documentation/matrix-completeness only — DES-AIRA2-001 enforces it locally to avoid a Depends-On cycle with DES-AIRA2-002), never the target account's own consent; must never issue a session for an account requiring MFA (enrolled or deployment-mandated) without a valid TOTP code first; must never call `SessionIssuer.issueSessionIfEligible` more than once per login attempt and must treat any non-success outcome (stale version, MFA no longer satisfied) as a full login failure with no session, never a retry that re-adopts the new state.
Requirements: REQ-MULTIUSER-001 REQ-MULTIUSER-002 REQ-MULTIUSER-007 REQ-MULTIUSER-010 REQ-MULTIUSER-022 REQ-MULTIUSER-035 REQ-MULTIUSER-050
ADRs: ADR-0002 ADR-0007
Depends-On: DES-AIRA2-011

## DES-AIRA2-002: Project Authorization & Sharing Service / プロジェクト認可・共有サービス
Responsibilities: Enforce default per-user project isolation; manage explicit project sharing and role grants (owner, editor, viewer); revoke access and terminate active sessions/MCP connections on revocation while preserving prior signed-record attribution; own and define the concrete project-scoped and self-scope authorization matrices below (covering ELN, Graph RAG, LLM backend configuration, and Agent Skills/MCP configuration actions), and be the enforcement point for every row via `authorize()`/`authorizeSelf()` EXCEPT `account.service-account.modify` and `team.membership.modify`/`team.admin.modify`/`team.delete`, whose policies it defines but whose enforcement is delegated to DES-AIRA2-001 and DES-AIRA2-013 respectively (see those rows' notes) because authentication must not depend on this service, and because team-admin resource data is stored only in DES-AIRA2-013; record a per-user audit log of authorization-relevant actions — this obligation (REQ-MULTIUSER-006) explicitly extends to every self-service mutation enforced via `authorizeSelf()` (profile update, email confirmation, password change/reset, TOTP enrollment/confirmation, session revocation) and every team mutation enforced by DES-AIRA2-013 (team create/delete/admin-assign/member-add/member-remove, team-share grant/revoke, invitation create/accept/cancel, member role change/removal), each recorded via the same `AuditLog.record({userId, timestamp, actionType, targetResource})` shape already used for `project.share.grant`/`revoke`, with `targetResource` never containing a raw password, TOTP code/secret, or invitation/reset token (CHANGE-0005); resolve the project role used by `authorize()` via a pluggable role resolver registered at composition-root startup — DES-AIRA2-013's `resolveEffectiveRole` (owner assignment, direct share, or team-based share) rather than a bare owner-assignment/direct-share lookup — so this service need not depend on DES-AIRA2-013 to consume it.
Interfaces: POST /projects/{id}/shares (actorContext, ``authorize(actorContext, projectId, 'project.share.manage')``), DELETE /projects/{id}/shares/{userId} (actorContext, ``authorize(actorContext, projectId, 'project.share.manage')``), GET /projects/{id}/authz-matrix, authorize(actorContext, projectId, action) -> allow|deny, authorizeSelf(actorContext, action) -> allow|deny (for actions scoped only to the caller's own account, no projectId required), on-revoke webhook to Session Service and MCP Gateway.
Constraints: Deny-by-default for any action not explicitly present in the authorization matrix. `authorize(actorContext, projectId, 'project.share.manage')` additionally grants when `actorContext` carries the global-admin role (checked directly, the same direct-role-check pattern as the self-scope `llmbackend.admin-credential.modify` rule below), independent of the caller's project role, so a global admin can grant/revoke shares on any project per REQ-MULTIUSER-004/005 even when not itself an owner/editor/viewer of that project; this is the only project-scoped action with a global-admin override, and it does not change the Y/N/N owner-only outcome for any non-admin caller. Concrete project-scoped matrix (rows = action, columns = owner/editor/viewer; Y=allowed, N=denied): project.share.manage Y/N/N; eln.view Y/Y/Y; eln.create Y/Y/N; eln.edit Y/Y/N; eln.approve Y/N/N; eln.sign Y/Y/N; eln.void Y/N/N; eln.export Y/Y/N; eln.audit-history.view Y/Y/N; eln.audit-integrity.manage Y/N/N; eln.audit-integrity.view Y/Y/N; graphrag.view Y/Y/Y; graphrag.create Y/Y/N; graphrag.modify Y/N/N; llmbackend.project-override.view Y/Y/Y; llmbackend.project-override.modify Y/N/N; credential.project.use Y/Y/Y; credential.project.view Y/N/N; agent-skills.view Y/Y/Y; agent-skills.modify Y/Y/N; mcp-config.view Y/Y/Y; mcp-config.modify Y/Y/N; agent-skill-source.manage Y/Y/N; agent-skill-source.sync Y/Y/N; mcp-provider.enable Y/Y/N. Self-scope matrix (rows = action, single column = policy; checked by `authorizeSelf(actorContext, action)` with no project role involved, EXCEPT the two explicitly-noted delegated-enforcement exceptions below): llmbackend.user-default.modify (any authenticated user, own account only); credential.user-override.modify (any authenticated user, own account only); credential.self.view (any authenticated user, own account only); llmbackend.admin-credential.modify (caller's global admin role only, checked directly against the account's role from DES-AIRA2-001 — this is the sole authoritative rule for that action; no project-scoped row for it exists or is needed); account.service-account.modify (caller's global admin role only — POLICY OWNED HERE, but ENFORCEMENT IS DELEGATED to DES-AIRA2-001, which performs a local direct `actorContext.roles` check rather than calling `authorizeSelf` on this service, because DES-AIRA2-001 must not depend on DES-AIRA2-002; this row is the first deliberate delegated-enforcement exception, for dependency-cycle avoidance); profile.self.update (any authenticated user, own account only, enforced normally by this service on behalf of DES-AIRA2-014); password.self.change (any authenticated user, own account only, enforced normally by this service; DES-AIRA2-014 additionally requires current-password re-verification before calling this check); mfa.self.enroll (any authenticated user, own account only, enforced normally by this service on behalf of DES-AIRA2-014); session.self.list (any authenticated user, own account only, enforced normally by this service on behalf of DES-AIRA2-015); session.self.revoke (any authenticated user, own account only, enforced normally by this service on behalf of DES-AIRA2-015); team.create (caller's global admin role only, enforced normally by this service — no per-resource team data is needed for this check); team.membership.modify / team.admin.modify / team.delete (caller's global admin role OR that specific team's own team admin — POLICY OWNED HERE, but ENFORCEMENT IS DELEGATED to DES-AIRA2-013, because determining "that team's own team admin" requires the team record, which only DES-AIRA2-013 stores; this row is the second deliberate delegated-enforcement exception, for data-locality reasons rather than dependency-cycle avoidance). Password-reset request/completion (REQ-MULTIUSER-020/032) is intentionally unauthenticated and has no matrix row: it is gated only by possession of the single-use reset token, never by `authorize()`/`authorizeSelf()`. Revocation must not alter historical signature attribution (REQ-MULTIUSER-012). Every action cited in any component's Interfaces or Constraints must have exactly one matching row in one of these two matrices; adding a new `authorize()`/`authorizeSelf()` call without a corresponding matrix row is a design defect. Every other backend component must call `authorize()` (for project-scoped actions) or `authorizeSelf()` (for self-scoped actions) through this service using a trusted actorContext (established by DES-AIRA2-001) rather than a bare caller-supplied userId/projectId; no component may query tenant-scoped rows without a preceding `authorize()`/`authorizeSelf()` call.
Requirements: REQ-MULTIUSER-003 REQ-MULTIUSER-004 REQ-MULTIUSER-005 REQ-MULTIUSER-006 REQ-MULTIUSER-008 REQ-MULTIUSER-009 REQ-MULTIUSER-011 REQ-MULTIUSER-012
ADRs: ADR-0005
Depends-On: DES-AIRA2-001 DES-AIRA2-011

## DES-AIRA2-003: Credential Vault / 認証情報保管庫
Responsibilities: Store LLM provider API keys and OAuth tokens encrypted at rest; hold administrator shared credentials and per-user override credentials; mask secret values on any read path; reject any credential write/read request the caller's authorized trust context does not permit for that scope.
Interfaces: setAdminSharedCredential(actorContext, provider, secret) -> credentialRef (``authorizeSelf(actorContext, 'llmbackend.admin-credential.modify')``, global admin role only), setUserOverrideCredential(actorContext, provider, secret) -> credentialRef (``authorizeSelf(actorContext, 'credential.user-override.modify')``, self-scope only, no projectId required), getCredentialForRequest(actorContext, projectId, provider) -> resolved secret (server-side only, `authorize(actorContext, projectId, 'credential.project.use')` via DES-AIRA2-002, actorContext carries the caller's authorized identity/roles; resolution is keyed by `(actorContext.accountId, provider)` and returns, in order: (1) the calling actor's own `setUserOverrideCredential` entry for that provider if present, else (2) the administrator shared credential for that provider set via `setAdminSharedCredential`; it must never return another account's override credential — DES-AIRA2-004's `chat()` relies on exactly this precedence per REQ-LLMBACKEND-004), listProjectCredentials(actorContext, projectId) -> masked entries (`authorize(actorContext, projectId, 'credential.project.view')` via DES-AIRA2-002), listSelfCredentials(actorContext) -> masked entries (``authorizeSelf(actorContext, 'credential.self.view')``, no projectId required).
Constraints: Plaintext secrets must never leave the vault process boundary; masked entries show only a fixed-length suffix; encryption keys must be rotatable without invalidating stored credential rows; every project-scoped method call (`getCredentialForRequest` via `credential.project.use`, `listProjectCredentials` via `credential.project.view`) must resolve `authorize(actorContext, projectId, action)` via DES-AIRA2-002 before touching stored secrets; every self-scoped or admin-global method call (`setUserOverrideCredential`, `listSelfCredentials`, `setAdminSharedCredential`) must instead resolve `authorizeSelf(actorContext, action)`, since none of these carries a projectId; all use a trusted actorContext propagated from DES-AIRA2-001/DES-AIRA2-002 rather than a bare caller-supplied userId/projectId.
Requirements: REQ-LLMBACKEND-003 REQ-LLMBACKEND-004 REQ-LLMBACKEND-005 REQ-LLMBACKEND-007
ADRs: ADR-0002
Depends-On: DES-AIRA2-001 DES-AIRA2-002 DES-AIRA2-011

## DES-AIRA2-004: LLM Backend Gateway / LLMバックエンドゲートウェイ
Responsibilities: Provide one adapter-based abstraction over GitHub Copilot CLI, OpenAI, Azure OpenAI, and Anthropic; let a user set their own default provider and let a project owner set a project-level override; resolve the effective backend for a request using project-override-then-user-default precedence; surface a user-visible fallback notice on backend failure; expose configured embedding-capability information per backend to Graph RAG.
Interfaces: LlmBackendAdapter { chat(), embed(), streamAgent() } implemented per provider, where a `BackendSelection` is the pair `{ providerId, model }` (model is provider-specific, e.g. an OpenAI/Azure OpenAI/Anthropic model name or the GitHub Copilot CLI default), setUserDefaultBackend(actorContext, selection: BackendSelection) (``authorizeSelf(actorContext, 'llmbackend.user-default.modify')``, no projectId required), setProjectBackendOverride(actorContext, projectId, selection: BackendSelection) (``authorize(actorContext, projectId, 'llmbackend.project-override.modify')`` via DES-AIRA2-002, owner only per the matrix's Y/N/N row — no separate project-admin role exists), resolveBackend(actorContext, projectId) -> BackendSelection (``authorize(actorContext, projectId, 'llmbackend.project-override.view')`` via DES-AIRA2-002; project-override-then-user-default precedence applies to the whole `{ providerId, model }` pair, not the provider alone), chat(actorContext, projectId, request) -> resolves the effective `BackendSelection` via `resolveBackend`, then resolves that request's credential via DES-AIRA2-003's `getCredentialForRequest(actorContext, projectId, selection.providerId)` (``authorize(actorContext, projectId, 'credential.project.use')`` via DES-AIRA2-002, Y/Y/Y — a per-request server-side credential use, distinct from the Y/N/N `credential.project.view` action that would disclose the raw secret value to the caller), then dispatches to that provider's adapter, constructed or configured per-request with the resolved credential and model (adapters are not pre-loaded with a single static credential at process startup), onBackendFailure(providerId) -> notice event, getEmbeddingCapabilities(providerId) -> matrix entry.
Constraints: Adapters must expose a common request/response contract regardless of provider; adding a fifth provider must not require changes to callers of resolveBackend; failure fallback must not silently switch providers without a visible notice; every call that reads or writes project-scoped backend configuration — including `resolveBackend` (action `llmbackend.project-override.view`), `chat` (actions `llmbackend.project-override.view` then `credential.project.use`), and `setProjectBackendOverride` (action `llmbackend.project-override.modify`), and not only configuration-changing calls — must pass an `authorize(actorContext, projectId, action)` check via DES-AIRA2-002 before DES-AIRA2-003 is touched; every call scoped only to the caller's own account (`setUserDefaultBackend`, action `llmbackend.user-default.modify`) must instead pass an `authorizeSelf(actorContext, action)` check, since it has no projectId; `chat` must never return or log the raw resolved credential value to the caller, only the backend's response.
Requirements: REQ-LLMBACKEND-001 REQ-LLMBACKEND-002 REQ-LLMBACKEND-006 REQ-LLMBACKEND-008
ADRs: ADR-0002
Depends-On: DES-AIRA2-002 DES-AIRA2-003 DES-AIRA2-011

## DES-AIRA2-005: ELN Core Service / ELNコアサービス
Responsibilities: Manage structured experiment records and their immutable, content-hashed versions; manage protocol/SOP authoring, versioning, and immutable version linkage from experiment records, enforcing that a linked protocol version's approval status (set only by DES-AIRA2-007) is "approved" before the link is accepted; link samples/reagents/inventory context into records; provide ELN search and reporting; integrate computational provenance references from executed notebooks.
Interfaces: POST /projects/{projectId}/eln/records (actorContext, `eln.create`; creates recordVersionId v1), PATCH /projects/{projectId}/eln/records/{id} (actorContext, `eln.edit`; creates a new immutable recordVersionId, content hash, and predecessor link; never mutates a prior version), GET /projects/{projectId}/eln/records/{id} (actorContext, `eln.view`), POST /projects/{projectId}/eln/records/{id}/export (actorContext, `eln.export`), DELETE /projects/{projectId}/eln/records/{id} (actorContext, `eln.void`; unsigned records only, see DES-AIRA2-007 for signed-record void), POST /projects/{projectId}/eln/protocols (actorContext, `eln.create`), POST /projects/{projectId}/eln/protocols/{id}/versions (actorContext, `eln.edit`), GET /projects/{projectId}/eln/search (actorContext, `eln.view`), GET /projects/{projectId}/eln/records/{id}/provenance (actorContext, `eln.view`), internal markProtocolVersionStatus(protocolVersionId, status) callable only by DES-AIRA2-007.
Constraints: Editing an experiment record must always create a new immutable, content-hashed version, never overwrite a prior one; a record's linked protocol version reference is immutable once set and must reference a protocol version whose status is "approved"; every state-changing command (create, edit, void, delete) must execute inside one atomic transaction that also commits the corresponding audit event via DES-AIRA2-006's internal writer — a command that cannot also commit its audit event must fail entirely; inventory/provenance links are read-only references to their source systems; all record/protocol reads and writes must resolve `authorize()` via DES-AIRA2-002 using a trusted actorContext.
Requirements: REQ-ELN-001 REQ-ELN-002 REQ-ELN-003 REQ-ELN-019 REQ-ELN-007 REQ-ELN-012 REQ-ELN-008 REQ-ELN-009
ADRs: ADR-0003
Depends-On: DES-AIRA2-002 DES-AIRA2-006 DES-AIRA2-011

## DES-AIRA2-006: ELN Audit & Integrity Subsystem / ELN監査・整合性サブシステム
Responsibilities: Provide an internal, trusted-only audit writer that DES-AIRA2-005 and DES-AIRA2-007 call within their own state-changing transactions (never exposed as a public API taking arbitrary before/after payloads) to append an immutable, chronologically ordered, per-project monotonically sequenced audit entry for every create/edit/view-sensitive/approve/void/export/delete action; run scheduled audit-trail integrity checks at least every 24 hours against a canonical, hash-chained representation of the log; block new electronic signature operations on tamper detection; track a `clearedAwaitingScheduledCheck` state after alert clearance and only lift the signing block when the next scheduled (not ad hoc) integrity check for that project completes clean.
Interfaces: appendAuditEntry(txContext, action, projectId, subjectType, subjectVersionId, actorContext) [internal, callable only from within a DES-AIRA2-005/007 transaction; `subjectType` is `record` or `protocol` and `subjectVersionId` is the corresponding immutable `recordVersionId`/`protocolVersionId` so both record-level and protocol-approval events are unambiguously attributable], getAuditHistory(actorContext, projectId, subjectType, subjectVersionId) -> auditEntry[] (`authorize(actorContext, projectId, 'eln.audit-history.view')` via DES-AIRA2-002; returns the ordered, per-project-sequenced audit entries recorded by `appendAuditEntry` for that record/protocol, satisfying REQ-MULTIUSER-009/011 and REQ-RUNTIME-003's ELN audit-history REST operation group), runIntegrityCheck(schedulerContext, projectId) [internal, `trigger=scheduled`, callable only by the trusted scheduler service principal], runManualIntegrityCheck(actorContext, projectId) -> report [`trigger=manual`, `authorize(actorContext, projectId, 'eln.audit-integrity.manage')`], clearTamperAlert(actorContext, projectId) [`authorize(actorContext, projectId, 'eln.audit-integrity.manage')`, transitions to clearedAwaitingScheduledCheck], isSigningBlocked(actorContext, projectId) -> boolean [`authorize(actorContext, projectId, 'eln.audit-integrity.view')`], getChainCheckpoint(actorContext, projectId) -> externally-anchored signed checkpoint [`authorize(actorContext, projectId, 'eln.audit-integrity.view')`].
Constraints: Audit entries are stored in an append-only store with database-level privilege separation where the persistence engine supports native DB roles/GRANTs; for a persistence engine without that model (SQLite, per ADR-0006), this is instead realized as an application-enforced insert-only discipline — no code path anywhere in the codebase issues `UPDATE`/`DELETE` against the audit table — combined with an OS-level file-permission boundary restricting write access to the server process's own account, and any correction possible only via a separate offline maintenance tool run by an operator outside the running server process (see DES-AIRA2-011); each entry's hash covers a canonical serialization of the payload plus a strictly increasing per-project sequence number and the previous entry's hash; the hash chain is periodically anchored by a checkpoint signed with a key unavailable to normal application writers, and that checkpoint/report is itself protected by the same tamper-evidence guarantee; only a scheduled integrity check that runs after `clearTamperAlert` may clear `clearedAwaitingScheduledCheck` and unblock signing — a manual check never can, regardless of caller role; every externally reachable read or write (manual check, alert clearance, signing-blocked query, checkpoint read) must resolve `authorize()` via DES-AIRA2-002 using a trusted actorContext and the concrete `eln.audit-integrity.manage`/`eln.audit-integrity.view` actions in DES-AIRA2-002's matrix; only the internal scheduled trigger is exempt, and it authenticates via a trusted scheduler service principal rather than a user-supplied actorContext.
Requirements: REQ-ELN-005 REQ-ELN-011 REQ-ELN-013 REQ-ELN-014 REQ-ELN-020
ADRs: ADR-0003
Depends-On: DES-AIRA2-002 DES-AIRA2-011

## DES-AIRA2-007: ELN Protocol Approval & Electronic Signature Subsystem / プロトコル承認・電子署名サブシステム
Responsibilities: Run the protocol approval workflow, and be the sole component permitted to set a protocol version's status to "approved" via DES-AIRA2-005's internal status callback; apply electronic signatures gated by unique-person re-authentication, binding each signature to one immutable recordVersionId/protocolVersionId and its content hash so a later edit cannot retroactively change what was signed; enforce separation of duties between author and approver; forbid automated/impersonated signatures; restrict edits to signed/approved records to non-destructive void (new successor versions may still be created and separately signed).
Interfaces: POST /projects/{projectId}/eln/protocols/{id}/versions/{versionId}/approve (actorContext, `eln.approve`), POST /projects/{projectId}/eln/records/{id}/versions/{versionId}/sign (actorContext, `eln.sign`; requires fresh re-auth challenge and the caller-supplied content hash to match the stored version's hash, using optimistic-concurrency preconditions), POST /projects/{projectId}/eln/records/{id}/void (actorContext, `eln.void`), GET /projects/{projectId}/eln/records/{id}/signature-status (actorContext, `eln.view`).
Constraints: A signature request must re-verify the signer's live credential (REQ-ELN-016), must reject if the signer account is not uniquely bound to one person (REQ-MULTIUSER-010) or is the same person as the record author where separation of duties applies, and must reject if the target recordVersionId's content hash has changed since the client last read it; every state-changing command (approve, sign, void) must execute inside one atomic transaction that also commits the corresponding audit event via DES-AIRA2-006's internal writer; only when DES-AIRA2-006 reports the project as not signing-blocked may a signature be accepted; all approval/signature reads and writes must resolve `authorize()` via DES-AIRA2-002 using a trusted actorContext.
Requirements: REQ-ELN-004 REQ-ELN-006 REQ-ELN-016 REQ-ELN-017 REQ-ELN-018 REQ-ELN-010 REQ-ELN-015
ADRs: ADR-0003
Depends-On: DES-AIRA2-002 DES-AIRA2-005 DES-AIRA2-006 DES-AIRA2-001 DES-AIRA2-011

## DES-AIRA2-008: Agent Skills & MCP Configuration Manager / Agent Skills・MCP設定マネージャー
Responsibilities: Manage per-project Agent Skills definitions and per-project MCP server configuration using the same file/config layout as AIRA; register one or more external Agent Skills repositories per project and synchronize skills from them on demand; act as the registration point through which built-in MCP providers (e.g. DES-AIRA2-009) are enabled per project using the same configuration surface as user-added MCP servers.
Interfaces: GET /projects/{projectId}/agent-skills (actorContext, `agent-skills.view`), PUT /projects/{projectId}/agent-skills (actorContext, `agent-skills.modify`), GET /projects/{projectId}/mcp-servers (actorContext, `mcp-config.view`), PUT /projects/{projectId}/mcp-servers (actorContext, `mcp-config.modify`), POST /projects/{projectId}/agent-skill-sources (actorContext, `agent-skill-source.manage`; register an external repository with its access credential), GET /projects/{projectId}/agent-skill-sources/{sourceId} (actorContext, `agent-skills.view`), DELETE /projects/{projectId}/agent-skill-sources/{sourceId} (actorContext, `agent-skill-source.manage`), POST /projects/{projectId}/agent-skill-sources/{sourceId}/sync (actorContext, `agent-skill-source.sync`; shows a diff before applying), POST /projects/{projectId}/mcp-servers/builtin/{providerId}/enable (actorContext, `mcp-provider.enable`).
Constraints: Configuration format and directory layout must remain compatible with AIRA so existing project configurations can be imported without transformation; sync must not silently overwrite local project-specific edits without a diff/confirmation step; every interface (view or modify agent skills, view or modify MCP server config, register/list/remove a repository source, sync a source, enable a built-in provider) must resolve `authorize(actorContext, projectId, action)` via DES-AIRA2-002 first, using distinct actions (`agent-skills.view`, `agent-skills.modify`, `mcp-config.view`, `mcp-config.modify`, `agent-skill-source.manage`, `agent-skill-source.sync`, `mcp-provider.enable`); registering, removing, or syncing a source and enabling a built-in provider require project owner/editor authorization, while viewing requires only project-member access.
Requirements: REQ-AGENTCONFIG-001 REQ-AGENTCONFIG-002 REQ-AGENTCONFIG-003
ADRs: ADR-0004
Depends-On: DES-AIRA2-002 DES-AIRA2-011

## DES-AIRA2-009: Graph RAG Service (aira-synapse merge) / Graph RAGサービス(aira-synapse統合)
Responsibilities: Provide, per project that has enabled it through DES-AIRA2-008, a built-in MCP server backed by its own supervised, project-isolated aira-graphdb (Rust) process and data directory; index documents and answer hybrid queries with resolvable citations; keep generation-time LLM backend consistent with the requesting project's configured backend; maintain a documented embedding-capability matrix (per LLM provider: native-embedding-capable yes/no, and the fallback embedding provider/model to use when not) and require re-indexing when a project's effective embedding model changes; support federated queries across only the projects the requesting user can access.

## DES-AIRA2-015: Session Registry & Credential Versioning / セッションレジストリ・資格情報バージョニング
Responsibilities: Maintain each account's monotonically increasing credential version, incrementing it exactly once per completed credential replacement (self-service change or reset, per DES-AIRA2-014); record, for every issued session, the credential version read atomically with that session's own issuance so no concurrent credential replacement can interleave between the read and the commit; reject at validation time any session whose recorded version no longer matches its account's current version; provide the authenticated user a listing of their own currently active sessions (a non-bearer display identifier, creation time, expiry time — never the bearer token value) and let them immediately invalidate any one of those sessions other than the one making the request; implement the `SessionIssuer` extension consumed by DES-AIRA2-001 at login, exposing a single atomic conditional-issuance operation that re-checks, at the moment of commit (not merely at an earlier check step), both that the credential version observed at credential verification is still current and that any required MFA condition is still satisfied, issuing a session only if both hold and otherwise failing with no session and no partial state change — closing the race where a concurrent credential replacement or MFA-state change completes between an earlier check and issuance.
Interfaces: issueSession(accountId) -> Session (unconditional atomic version-read-and-record, used by DES-AIRA2-014 for password-change session reissuance, where the caller has already incremented the version itself), `issueSessionIfEligible(accountId, versionAtVerification, mfaSatisfied) -> Session | {status:'stale-version'} | {status:'mfa-required'}` (the `SessionIssuer` extension operation, called exactly once by DES-AIRA2-001's login flow as its final step; atomically re-reads the account's current credential version — via this component's own store-backed `credential_versions` table — and current MFA-required state via the registered `MfaRequirementReader.isMfaRequired(accountId)` extension (implemented by DES-AIRA2-014, registered at composition-root the same way as `MfaCheck`/`SessionIssuer`, for the same Depends-On-cycle-avoidance reason: this is a read-only query of DES-AIRA2-014's `totp_factors.active` flag, not a call into any of its atomic write operations) in the same `runInTransaction` block as the compare against `versionAtVerification`/`mfaSatisfied` and the session insert, so no window exists between the re-check and the commit), validateSession(token) -> actorContext|invalid (rejects on version mismatch), listSessions(actorContext) -> [{displayId, createdAt, expiresAt}] (``authorizeSelf(actorContext, 'session.self.list')``), revokeSession(actorContext, displayId) (``authorizeSelf(actorContext, 'session.self.revoke')``, rejects targeting the caller's own current session id), incrementCredentialVersion(accountId) -> newVersion (called by DES-AIRA2-014 inside its atomic password-change/reset operation). Per this CHANGE, the constructor accepts DES-AIRA2-011's `SqliteStore` and persists sessions through its pre-existing `sessions` table (`upsertSession`/`getSession`/`deleteSession`, previously unused here, plus a new `listSessionsByAccount` query added for `listSessions`) and each account's credential version through a new `credential_versions` table, replacing this component's previous private `Map` fields with no change to any method above.
Constraints: `issueSessionIfEligible` must perform its version/MFA re-check and the session insert as a single atomic step (via `runInTransaction`) with no observable window in which a concurrent `incrementCredentialVersion` or MFA-state change could occur without being reflected in the outcome (REQ-MULTIUSER-050) — it must never issue a session on a stale version or unsatisfied MFA requirement, and must never be retried by the caller to "adopt" the new state after a `stale-version`/`mfa-required` result; `issueSession` (the unconditional form) may only be called by a caller that itself just performed the corresponding credential-version increment inside the same logical operation, never by the login path; `listSessions`/`revokeSession` must never return or accept a raw bearer token as the session identifier, using an opaque display identifier instead; revocation must take effect before the call returns success, such that an immediately subsequent request bearing the revoked session's token is rejected.
